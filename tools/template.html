EC2 Nitro Sandbox 实测：只有镜像没被改过的 Sandbox 才拿得到 KMS 里的密钥，instance store 读得和直测一样快

在一台 i7i.2xlarge 上从零搭起来，测三件事：KMS 能不能只对 PCR 匹配的 Sandbox 放行；以太坊交易怎么签、谁能签； 把整块 instance store 交给 Sandbox 之后读写有多快。下面 {{NSTEPS}} 步照着做大约一个半小时，能得到和这里一样的结果。每一步执行的都是仓库里的脚本。

测的是什么

所有测试都在同一台 parent 上做。Sandbox 是 parent 上用 Firecracker 起的 microVM，Nitro 把它的内存和 parent 隔开，并通过 /dev/nsm 给出签过名的 attestation 文档。

机器
i7i.2xlarge（8 vCPU，64 GiB），1 块 1875 GB NVMe instance store，us-west-1 按需价 $0.83/小时；实例角色 nitro-sandbox-workshop
系统
Amazon Linux 2023，kernel 6.18.62，Firecracker v1.18.0，内存池 48 GiB
Sandbox
confidential 模式（非 debug），4 个独占 vCPU，4 GiB 内存；内核用 parent 的 /boot/vmlinuz，initrd 由 dracut 生成，rootfs 是 Ubuntu 24.04
A 部分
fio direct=1：大文件写入、大块顺序写、顺序读、4K 随机读、4K 随机写、QD1 读延迟，parent 直测和 Sandbox 各跑一遍
B 部分
KMS key 只认这台 Sandbox 的 PCR0：带 attestation 解密和 ETH 钱包；不带 attestation、parent、封口、改镜像、debug 模式都必须被拒；外加 KMS Sign 签 ETH 交易和 Sepolia 真转一笔
机器分工
标着"工作机"的步骤在你自己的电脑上做（装好 AWS CLI v2、git、python3），其余都在 parent 上做；两边都要 clone 这个仓库。Sandbox 里不用手动操作，脚本会自己 ssh 进去

{{RANGE_NOTE}}

io_engine 一定要写 Async

Firecracker 块设备默认用 Sync 引擎，一次只处理一个请求，队列深度再大也没用。第 {{S_SYNC}} 步实测：同样的盘、同样的 fio，Sync 下 4K 随机读只有 Async 的 1/{{SYNC_X}}。

Sandbox，AsyncSandbox，Sync（默认）

怎么看

  • 读几乎不受影响。顺序读是直测的 {{SEQREAD_PCT}}%，4K 随机读是 {{RANDREAD_PCT}}%。代价在延迟：每次读多 {{LAT_ADD}} µs（经过 virtio、DMB 和 Firecracker 用户态），p99 从 83 µs 变成 230 µs。
  • 大块写和大文件写只有直测的 {{BIGFILE_PCT}}% 左右（约 {{SANDBOX_WRITE}} MB/s）。Firecracker 打开设备时不用 O_DIRECT，写入要先进 parent 的 page cache 再回写，fsync 要等回写完成。这是 Sandbox 写入的瓶颈，调 DMB 大小没有用。
  • 4K 随机写是直测的 {{RANDWRITE_PCT}}%，不代表 Sandbox 写得更快。直测是纯随机的 4K O_DIRECT；Sandbox 的写先进 parent 的 page cache，内核回写时按偏移排序、把相邻的 4K 合并成大块。fsync 的时间已经算进去了。测试区越大、写得越分散，这个优势越小。
  • parent 能读到 Sandbox 写进盘的明文（数据路径经过 parent）。需要保密就在 Sandbox 里用 dm-crypt 加密，实测开销几乎为零；要防篡改再加 dm-integrity（LUKS2 AEAD），代价主要在写：随机写降到 1/8 左右，一次 fdatasync 约 440 µs。

B. Attestation 和 ETH 签名

先建一把只认这台 Sandbox 的 PCR0 的 KMS key，然后逐一试：谁能解密、谁能拿到 ETH 钱包私钥、谁能让 KMS 签交易。步骤顺序就是实测时的顺序，后面的步骤依赖前面留下的密文和钱包。

ETH

怎么看

  • attestation 管的是"启动时是什么镜像"。内核、initrd、cmdline 有一点不同 PCR0 就变；同样的镜像每次启动 PCR0 都一样，所以可以把它写进 key policy。
  • rootfs 不在度量范围内。这个测试镜像的 rootfs 里还有 sshd 和 Python，进到 Sandbox 里的人照样能调 KMS。正式使用要把服务放进 initrd（或者用 dm-verity，把 root hash 写进 cmdline），去掉 SSH，并在启动取完密钥后马上封口。
  • 两种 ETH 方案的边界不同。KMS Sign：私钥永远不出 KMS，但谁有实例角色谁就能签（parent 也能）。attestation 钱包：只有 PCR0 匹配、没封口的 Sandbox 能拿到私钥，parent 拿不到；代价是私钥会出现在 Sandbox 内存里。
  • KMS 分不出 Sandbox 和 parent。两者用同一个实例角色，出口 IP 也一样（都经过 parent 的 NAT）；能区分它们的只有 attestation 文档。
